# Kubriko Showcase release notes

Produce **one** throwaway file holding the Showcase app's "what's new", in the forms the pipelines take,
so the user can paste the same text into every workflow they dispatch for the release and every store
page they fill in by hand. The text has to be complete as it is — nothing to fill in, nothing to trim
before pasting.

**The Showcase is an app, and the notes are for the people who install it** from Google Play, the App
Store, Steam or the web — people trying out the games and demos, not developers reading the source. No
module names, class names, Gradle, Managers or Traits.

## Process

1. **Determine the version.** The release is `showcase.versionName` in `gradle.properties`, and
   `showcase.buildNumber` is the build number every platform shares. Read the file with the Read tool
   (or `grep -a`): its copyright line can make plain `grep` treat it as binary and print nothing.

2. **Find the previous release boundary.** Showcase version bumps are commits titled
   `Increment Showcase app version number to "vX.Y.Z"`:
   ```bash
   git log --format='%H %ad %s' --date=short | grep 'Increment Showcase app version number' | head -3
   ```
   When the current `showcase.versionName` has already been bumped, the range starts at the bump
   *before* it; otherwise it starts at the last bump. The range is `<boundary>..HEAD`.

3. **List the commits that can reach a player:**
   ```bash
   git log <boundary>..HEAD --format='%H %s' -- app examples engine plugins
   ```
   A production Showcase build is made with `areTestExamplesEnabled=false`, `isDebugMenuEnabled=false`,
   `isSceneEditorEnabled=false` and `shouldShowUnfinishedGames=true`. So changes to the `examples/test-*`
   modules, the debug menu and the scene editor never reach a player and are left out. Unfinished games
   do reach one.

4. **Read the actual diffs — never summarize from commit subjects.** For each commit:
   ```bash
   git show <hash>
   ```
   User-visible strings say the most about what a player will see:
   ```bash
   git diff <boundary>..HEAD -- '*composeResources/values/strings.xml'
   ```

5. **Keep what a player could notice.** New games or demos, new content or levels in existing ones,
   gameplay and control changes, gamepad/keyboard/touch support, new settings, visible design changes,
   fixed crashes and bugs a player could hit, and performance someone can feel (smoother frame rate,
   faster loading, lower battery use). Engine and plugin changes count **only through their effect on
   the Showcase** ("Smoother particle effects", not "`ParticleManager` batches by drawing order"). Drop
   refactors, dependency bumps, tests, CI, build configuration and documentation.

6. **Note the platform** when a change is true on only some of them ("on Android", "in the browser
   version"). Code in `commonMain` needs no qualifier; code under `app/<platform>` or in a `<platform>Main`
   source set usually does.

7. **Write the file** to `.release-notes/showcase-<version>.md` (create the directory; `/.release-notes/`
   is gitignored). Its contents are exactly the layout below and nothing else — no preamble, no
   "generated by":

   ````
   ## Workflow input (release_notes)

   ```
   - First bullet\n- Second bullet\n- Third bullet
   ```

   ## Plain text

   ```
   - First bullet
   - Second bullet
   - Third bullet
   ```
   ````

   Both blocks hold the same text. Generate the escaped line from the plain text with a real
   interpreter (join the lines with a literal `\n`) instead of retyping it. Then check the plain text
   with Python's `len()` and report the character count.

8. **Report back briefly:**
   - the path, and that the file is a throwaway to delete after pasting;
   - the character count against the 500 limit;
   - that the escaped line goes into the `release_notes` input of both `[Showcase] Publish Android` and
     `[Showcase] Publish iOS`, and the plain text into anything filled in by hand (the Steam
     announcement, a store console);
   - whether `showcase.versionName` and `showcase.buildNumber` look raised since the boundary commit.
     If either is unchanged, say so: Play and App Store Connect both refuse a build number they have
     seen, and Apple takes no new build for a version already on the store.

9. **Do not dispatch a workflow, bump a version, or commit anything.** Drafting the notes is the whole
   job.

## Style

- **A flat list of `-` bullets**, one per line. No headings, no sections, no grouping by type.
- **Most interesting first:** a new game or demo, then smaller additions, then fixes.
- **Each bullet is a short noun phrase or plain sentence with no trailing period** (`New demo: isometric
  city builder`, `Gamepad support in every game`, `Fixed a crash when resuming Wallbreaker`).
- **Plain language, the player's vocabulary.** Name games and demos the way the Showcase menu does.
- **Short.** Three to six bullets for a feature release, one or two for a patch. Merge small fixes in one
  area into one bullet rather than listing each commit.
- **500 characters at most**, newlines included — Google Play's limit, the tightest of the stores and
  one the Android workflow cuts at. Shorten wording before dropping a bullet.
- **Plain text only**: no markdown, links, bold, backticks or emoji, since the stores show it as it is.
- **No backslashes and no other `\` escapes.** The workflows expand the input with `printf '%b'`, so only
  `\n` may appear, and only in the escaped line.
- No version numbers in the bullets, and no marketing adjectives.
